# v227 — Saved-Search Notification Audit Persistence Design

## Checkpoint identity

- Marker: `V227_SAVED_SEARCH_NOTIFICATION_AUDIT_PERSISTENCE_DESIGN`
- Base checkpoint:
  `project-checkpoint-v226-saved-search-notification-admin-ux-surfacing`
- Target checkpoint:
  `project-checkpoint-v227-saved-search-notification-audit-persistence-design`
- Checkpoint type: design-only
- Runtime implementation: explicitly out of scope

## Purpose

The existing saved-search notification audit and observability surfaces provide
deterministic reports and rollback evidence, but they do not yet define a
durable database record for every notification lifecycle decision.

v227 defines the persistence contract for an append-only audit event without
creating the model, migration, write service, scheduler integration, admin
interface, delivery action, rollback action, or retention job.

## Proposed persistent model

Future implementation name:

`SavedSearchNotificationAuditEvent`

This model is not created in v227.

### Identity fields

- `id`: UUID primary key generated by the application.
- `saved_search`: protected foreign key to `SavedSearch`.
- `owner_id_snapshot`: immutable owner identifier captured when the event is
  written.
- `event_type`: stable machine-readable lifecycle event.
- `outcome`: normalized result state.
- `reason_code`: stable reason suitable for filtering and reporting.
- `occurred_at`: application-supplied timezone-aware event time.
- `created_at`: database insertion time.

### Correlation and idempotency fields

- `batch_id`: groups events produced by one scheduler or operator batch.
- `correlation_id`: groups the complete lifecycle of one notification
  evaluation.
- `delivery_attempt_id`: identifies one external delivery attempt.
- `idempotency_key`: stable unique key preventing duplicate persistence.
- `notification_fingerprint`: deterministic fingerprint of the logical
  notification candidate.
- `rollback_of`: protected self-reference linking a compensating event to the
  original event.

### Actor and source fields

- `actor_type`: `system`, `scheduler`, `operator`, `management_command`, or
  `test_backend`.
- `actor_identifier`: stable non-secret identifier for the initiating actor.
- `source`: stable source component or command name.

### Timestamp transition snapshots

- `checked_at_before`
- `checked_at_after`
- `sent_at_before`
- `sent_at_after`

These fields record the timestamp transition. They do not themselves mutate
the `SavedSearch` row.

### Metadata

`metadata` is a JSON object limited to allow-listed operational context.

It must not contain:

- Rendered plain-text email bodies.
- Rendered HTML email bodies.
- Authentication credentials.
- API keys.
- SMTP secrets.
- Session tokens.
- Raw exception tracebacks containing secrets.
- Unredacted arbitrary request data.

## Event taxonomy

The initial stable event types are:

1. `evaluation_started`
2. `skipped_notifications_disabled`
3. `skipped_missing_recipient`
4. `dry_run_rendered`
5. `delivery_attempted`
6. `delivery_succeeded`
7. `delivery_failed`
8. `sent_timestamp_recorded`
9. `rollback_previewed`
10. `rollback_applied`

Initial normalized outcomes are:

- `pending`
- `skipped`
- `succeeded`
- `failed`
- `rolled_back`

New event types may be added. Existing event type meanings must not be silently
redefined.

## Append-only and immutability contract

Audit events are immutable persisted records.

Application code must not update an existing event to represent a later
lifecycle state. A later state is represented by a new event sharing the same
correlation identifiers.

Normal application and admin paths must not expose edit or delete operations.

Corrections and rollback operations create compensating events. They do not
rewrite or delete historical events.

The proposed model intentionally has no general-purpose `updated_at` field.

## Idempotency contract

Every write operation must supply an idempotency key derived from stable inputs.

At minimum, the key must distinguish:

- Event type.
- Saved-search identity.
- Notification fingerprint.
- Delivery attempt or rollback identity.
- Relevant scheduler or command execution.

A database uniqueness constraint on `idempotency_key` is required.

Duplicate attempts must load or report the existing event rather than create a
second logical event.

The notification fingerprint must remain compatible with the stable
fingerprint behavior preserved by v224.

## Transaction boundaries

### Evaluation and skip events

Evaluation and skip events may be written after their deterministic decision
is complete. They must not mutate notification timestamps.

### Delivery attempts

External email delivery cannot be made atomic with the local database
transaction.

The lifecycle therefore uses separate events:

1. Persist `delivery_attempted`.
2. Execute the explicitly authorized delivery operation.
3. Persist either `delivery_succeeded` or `delivery_failed`.
4. When delivery succeeds, update `last_notification_sent_at` and persist
   `sent_timestamp_recorded` inside the same database transaction.

A stable `delivery_attempt_id` and idempotency key must prevent duplicate
logical sends or duplicate success records.

### Rollback

A timestamp rollback and its `rollback_applied` audit event must occur in the
same database transaction.

`rollback_of` must reference the event whose effect is being compensated.

A rollback must preserve `last_notification_checked_at` unless an independent
explicit contract authorizes changing it.

## Failure behavior

Audit persistence failure must be explicit and observable.

For a future production-delivery path:

- Failure to persist `delivery_attempted` blocks delivery.
- Failure to persist a failed-delivery event must surface as an operator-visible
  error.
- Failure to persist the success/timestamp transaction must not be reported as
  a completed local state transition.
- Retrying must use the same idempotency and correlation identifiers.

No v227 code delivers email or changes these runtime behaviors.

## Privacy minimization

The audit record stores identifiers and operational outcomes, not message
content.

Recipient handling should prefer the saved-search owner relation or a
non-reversible recipient fingerprint. A full recipient address snapshot should
only be introduced after a separate privacy review and documented retention
requirement.

Metadata keys must be allow-listed.

## Index and query design

Future implementation should provide indexes for:

- `(saved_search, occurred_at)`
- `(event_type, occurred_at)`
- `(outcome, occurred_at)`
- `batch_id`
- `correlation_id`
- `delivery_attempt_id`
- `notification_fingerprint`
- `rollback_of`

`idempotency_key` requires a unique constraint.

## Retention policy

Audit records require an explicit retention policy before production
persistence is enabled.

The policy must define:

- Default retention duration.
- Legal or support hold behavior.
- Which metadata is removed or anonymized first.
- Operator authorization for export.
- Deletion or anonymization evidence.
- Behavior for audit records whose saved search or owner is removed.

Retention enforcement is not implemented in v227.

## Operator access

The future operator interface is read-only by default.

It should support filtering by:

- Saved search.
- Owner identifier.
- Event type.
- Outcome.
- Date range.
- Batch identifier.
- Correlation identifier.
- Delivery attempt identifier.
- Notification fingerprint.

It must not provide delivery, retry, rollback, edit, or delete actions merely
because the event is visible.

## Rollout phases

1. Schema contract.
2. Migration implementation.
3. Append-only write service.
4. Scheduler integration.
5. Rollback integration.
6. Read-only operator interface.
7. Retention enforcement.

Each phase must have focused tests and must preserve the explicit delivery
guardrails established by v219 through v226.

## Explicit v227 exclusions

v227:

- Does not create `SavedSearchNotificationAuditEvent`.
- Does not add a migration.
- Does not change `SavedSearch`.
- Does not change admin runtime behavior.
- Does not add audit writes.
- Does not deliver email.
- Does not add automatic scheduling.
- Does not add background processing.
- Does not add retry behavior.
- Does not add admin delivery actions.
- Does not add admin rollback actions.
- Does not mutate notification timestamps.
- Does not change templates.
- Does not change settings or secrets.
- Does not create `backend/docs`.

Only the v227 test and v227 root design document should be staged.

## Acceptance criteria

- The design defines append-only audit event identity.
- The design defines immutable persisted records.
- The design defines a stable idempotency key.
- The design defines a stable notification fingerprint.
- The design defines correlation and batch identifiers.
- The design defines explicit rollback linkage.
- The design defines transaction boundaries.
- The design defines privacy minimization.
- The design defines a retention policy.
- The design defines operator read access.
- Existing v223–v226 audit, rollback, delivery-design, and admin UX checkpoints
  remain green.
- Full regression remains green.
- No runtime or migration file changes.
